# B104G — Complete GraphSAGE row reconstruction, full-matrix validation, and Entrez-native GO controls

## Executive conclusion

The previous statement that the 121 label columns matched exactly was initially limited to 56,411 of 56,944 GraphSAGE rows whose Entrez identities had been recovered independently from graph topology and input features. The remaining 533 rows were known only as members of 183 topology/feature-equivalence classes.

B104G removes that row-level limitation. A deterministic legacy-Python node-order model assigns an Entrez GeneID to every one of the 56,944 GraphSAGE rows. The model:

1. reads each selected OhmNet tissue edgelist in its original line order;
2. keeps node tokens as strings;
3. inserts the tokens into a simulated 64-bit, unrandomized CPython 2.7 dictionary as the graph is built; and
4. iterates the dictionary table from low slot to high slot to obtain the tissue-local node order.

This order agrees with all 56,411 row identities that had previously been resolved without using labels. It disagrees with none of them. It also resolves every one of the 183 former equivalence classes to exactly its previously established candidate-GeneID set.

Under this strongly supported full row-to-Entrez reconstruction:

- all 24 GraphSAGE graph blocks have exactly the node and edge sets of their assigned OhmNet tissue networks;
- all 818,716 GraphSAGE undirected links, including self-loops already present in the source JSON, are verified;
- all 2,847,200 feature cells, 56,944 rows × 50 columns, are reproduced exactly;
- all 6,890,224 label cells, 56,944 rows × 121 columns, are reproduced exactly;
- repeated appearances of the same Entrez GeneID have no conflicting feature or label vectors.

The exact row values are therefore reproduced for the complete GraphSAGE PPI input, not merely for a subset or only as equivalence-class multisets.

The claim still requires careful wording: the full row assignment is an inference from deterministic legacy serialization behavior that is supported by several independent exact checks. The original preprocessing source code has not been located, so the historical implementation itself is not source-code proven.

## Correction of the earlier scope statement

The earlier result had two levels:

- **56,411 rows:** exact row-to-GeneID identity and exact label comparison.
- **533 rows in 183 classes:** only equality of the observed and predicted label-vector multisets within each class.

That class-level result proved that a compatible assignment existed, but it did not identify which anonymous row was which gene inside every class.

B104G supplies that missing row order. The 533 rows are no longer unresolved under the inferred serialization model. No labels were used to choose their order.

## Full row-order reconstruction

### Accepted model

For each tissue network, insert the endpoint strings encountered while scanning the original OhmNet edgelist into a 64-bit unrandomized CPython 2 dictionary. The GraphSAGE local row sequence is the resulting internal table-iteration order.

The crucial details are:

- node tokens remain strings;
- insertion occurs as edgelist rows are read;
- the historical CPython 2 string hash and dictionary probing/resizing rules are used;
- iteration scans occupied table slots in increasing slot order.

|---|---:|

The accepted model also reproduces the candidate-GeneID set in all 183 former equivalence classes and gives 4,301 distinct Entrez GeneIDs across the 56,944 tissue-specific row instances.

### Independent validations

A separately written implementation reconstructed the complete row order and compared it with the primary 56,944-row mapping:

- 56,944 / 56,944 row assignments identical;
- zero node-set discrepancies across 24 tissues;
- zero edge-set discrepancies across 24 tissues;
- no GeneID with conflicting repeated feature vectors;
- no GeneID with conflicting repeated label vectors.

The row-order result is additionally consistent with an independent positive control from earlier work: the same CPython 2 dictionary simulator reproduced the entire irregular JSON-key order of all 56,944 entries in `ppi-class_map.json`.

## Complete topology validation

Using the full mapping:

- 24 / 24 GraphSAGE graph blocks have the exact expected OhmNet node set;
- 24 / 24 have the exact expected OhmNet edge set;
- all 818,716 GraphSAGE undirected links, including loops, are verified;
- no link joins different tissue blocks.

This resolves the anonymous-row identity problem, but it does not yet explain why these particular 24 tissues were chosen from the 144 OhmNet networks or why they received the observed 20/2/2 train/validation/test assignment.

### ATP6AP2

GeneID 10159, ATP6AP2, remains outside the release-159 GPI object mapping used for GOA projection. The complete row-order reconstruction nevertheless identifies its GraphSAGE row from the OhmNet network node ID. Its deposited 121-vector is all zero, and the fixed predictor also gives an all-zero vector. Therefore this unresolved GPI correspondence does not conceal a label mismatch.

### Source-mechanism caution

Release 159 is the only GOA release from 158 through 169 that is exact under the fixed transformation. That is strong source-date evidence. It does not prove that the original script opened the GOA release-159 GAF directly; an Entrez-native or preprocessed annotation product containing the same effective associations could generate the same output.

## GO term identities and column order

The matrix uniquely determines 115 column identities. Six columns form three pairs in which two GO terms have identical membership vectors on all 4,301 graph genes:

| Column pair | Candidate terms |
|---|---|
| 24 / 71 | GO:0043228 and GO:0043232 |
| 39 / 63 | GO:0006464 and GO:0036211 |
| 48 / 70 | GO:0043230 and GO:1903561 |

The full row reconstruction does not distinguish these pairs; the candidate vectors remain identical across all 4,301 genes.

The existing CPython 2 column-order analysis strongly supports this provisional orientation:

- column 24 → GO:0043228; column 71 → GO:0043232;
- column 39 → GO:0006464; column 63 → GO:0036211;
- column 48 → GO:1903561; column 70 → GO:0043230.

This orientation is not proven. The best plausible ordering model has a longest common subsequence of 94 of 121 and does not reproduce every absolute position. Original source code, an ordered term list, or a perfect reconstruction of dictionary insertion history is needed for proof.

## Entrez-native dhimmel controls

The four genuine commit-pinned human annotation files were parsed and compared against all 121 complete GraphSAGE columns. None directly reproduces even one entire GraphSAGE label column when searched across its own terms.

| File | Terms | Selected GO IDs present | Exact columns using selected ID | Exact columns using any term | Closest mismatch |
|---|---:|---:|---:|---:|---:|
| direct, all evidence | 16,440 | 56 | 0 | 0 | 9 genes |
| direct, experimental | 10,174 | 39 | 0 | 0 | 1 gene |
| inferred, all evidence | 20,671 | 114 | 0 | 0 | 9 genes |
| inferred, experimental | 14,797 | 114 | 0 | 0 | 1 gene |

The closest file, inferred experimental evidence, has 74 columns at at least 95% agreement and six at at least 99%, but zero exact columns. This is consistent with its documented policy differing from the exact GraphSAGE transformation: it includes IPI in the experimental set and propagates through both `is_a` and ontology `part_of`.

The Entrez-native control is nevertheless informative for the nested-gene mapping issue. Its inferred experimental table gives GeneID 25788, RAD54B, the exact 19 selected labels observed for that gene, without importing FSBP annotations. It is not the full label source because it predicts 44 selected labels for ATP6AP2, whose GraphSAGE row is all zero.

The source-row order of these summary tables also does not solve the GraphSAGE label-column order. Their best Python-2-dictionary control reaches LCS 79, below the best GOA-derived LCS 94.

## Opportunities to disambiguate further

### 1. Locate or reconstruct the original preprocessing program

Search repositories, web archives, manuscript supplements, and author backups for code containing combinations of:

- `read_edgelist`, `disjoint_union`, `convert_node_labels_to_integers`, or `node_link_data`;
- `ppi-class_map.json`, `ppi-id_map.json`, or `ppi-feats.npy`;
- thresholds near 1,000 and 200;
- a feature cap of 50;
- GO evidence-code lists;
- serialization under Python 2 / NetworkX 1.x.

Finding the code would elevate the row order and feature/label selection from strongly supported reconstructions to direct provenance.

### 2. Finish the exact GO column-order search

The remaining high-value candidate constructions are:

- exact late-June ontology key and stanza order;
- historical `gene2go` row order;
- `org.Hs.eg.db` 3.3.0 and 3.4.0 internal table/map order;
- separate dictionaries for direct versus propagated annotations;
- gene→GO versus GO→gene insertion, including intermediate set/dict objects;
- the exact selected-term list before JSON emission.

A perfect, independently motivated order would resolve the three duplicate-vector orientations.

### 3. Recover the 24-network selection and split rule

Simple edge-count rules do not recover the selected set:

- 105 of 144 networks have at least 15,000 undirected edges;
- 36 have at least 35,000;
- not all selected training networks reach 15,000;
- not all validation/test networks reach 35,000;
- the selected set is not the 24 largest networks.

Next tests should distinguish directed-edge counts from undirected counts, full networks from largest connected components, and source-version differences. Original random seeds or an explicit tissue list in preprocessing code would be decisive.

### 4. Determine the literal GO annotation source

The exact output is compatible with GOA release 159 plus the documented mapping rules. The genuine dhimmel summaries are not exact. Additional controls remain useful:

- historical NCBI `gene2go` and `gene2accession`;
- Bioconductor `org.Hs.eg.db` 3.3.0 and 3.4.0;
- HumanBase/Sleipnir intermediate annotation products;
- exact late-June ontology robustness.

These tests may identify an Entrez-native source that produces the same matrix without the semantic UniProt component handling.

### 5. Audit ATP6AP2 for provenance only

A date-matched UniProt or NCBI record can explain why ATP6AP2 is absent from GPI159. This cannot improve the observed matrix because its complete deposited label vector is zero, but it would close a provenance gap.
