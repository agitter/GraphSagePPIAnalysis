# Staged upload, analysis, provenance, and deletion protocol

## Objective

Use only one raw-data batch at a time. Before raw uploads, collect a small checksum inventory so public files can be downloaded independently and duplicate uploads can be avoided. A raw batch is not cleared for deletion until its bytes, provenance, parse results, derived data, and analysis outputs have all been reconciled and recorded.

## Batch lifecycle

Every file moves through these states:

1. `planned` — named in the source ledger but not present.
2. `inventory_reported` — filename, byte size, SHA-256, and local provenance supplied in the small inventory CSV.
3. `received` — raw file uploaded and mounted.
4. `integrity_verified` — size and SHA-256 agree with the inventory; archive/compression tests pass.
5. `parsed` — format, headers, release metadata, row counts, identifiers, taxon coverage, and parser warnings recorded.
6. `analyzed` — the planned comparisons for the batch completed.
7. `derived_verified` — retained normalized data re-read successfully and reconciled to raw input counts.
8. `deletion_clearance_issued` — an explicit clearance lists exact filenames and SHA-256 values.
9. `deletion_confirmed_by_user` — the user reports that the uploaded raw files were removed.
10. `raw_deleted_derived_retained` — ledger records that raw bytes are unavailable in the conversation but verified derived artifacts and reacquisition information remain.

A file stays on `hold_raw` instead of moving to deletion clearance when later batches need byte-level cross-comparison that cannot be performed from the retained derivative.

## Manifest fields maintained for every batch

The existing detailed source fields remain mandatory: artifact name, source URL, source page, retrieval method/status, local path/status, byte size, SHA-256, analysis role, consuming scripts, parent/derivation, and notes.

The following lifecycle fields are added for staged uploads:

- `batch_id`
- `inventory_sha256`
- `received_at_utc`
- `integrity_verified_at_utc`
- `analysis_completed_at_utc`
- `deletion_clearance_issued_at_utc`
- `user_deletion_confirmed_at_utc`
- `raw_retention_status`
- `raw_available_in_conversation`
- `retained_derivative_paths`
- `derivative_sha256s`
- `parser_version_or_script_sha256`
- `raw_to_derived_reconciliation`
- `reacquisition_url`
- `deletion_notes`

Events are append-only. A later correction does not overwrite the earlier record; it adds a superseding event and explains the change.

## What is retained before deletion

For GO annotation batches, retained derivatives will preserve at least:

- every original header/comment line;
- release and format versions;
- all columns needed to reconstruct the tested gene–GO relations, including qualifiers, evidence codes, references, taxon, dates, assigned-by values, object types, and extensions;
- complete GPI identifier and xref fields needed for alternative mappings;
- the human rows relevant to the recovered GraphSAGE/OhmNet gene universe, plus any mapping rows needed to reach those genes;
- ontology term IDs, namespaces, obsolete/replacement information, `is_a`, and tested `part_of` relations;
- parse warnings, rejected-row records, source/derived row counts, and both compressed and uncompressed checksums where applicable;
- exact analysis parameters and the hash of the code that produced each derivative.

A compact derivative is accepted only after it can be re-read and independently reproduces the raw-source counts relevant to the analysis.

## Upload schedule

### Batch 0 — inventory only

Upload the datestamped inventory generated by `make_local_inventory.py`, for example `local_upload_inventory_20260827T154233Z.csv`. No database archives are uploaded in this batch. The script always inserts the current UTC datestamp (`YYYYMMDDTHHMMSSZ`) before the `.csv` suffix. An explicit `--datestamp` can be supplied for deterministic naming.

Example:

```bash
python make_local_inventory.py /path/to/your/files \
  --patterns-file requested_file_patterns.txt \
  --output local_upload_inventory.csv
```

The command above writes a file such as `local_upload_inventory_20260827T154233Z.csv`. The inventory determines exact batch sizes and lets public files be acquired independently before requesting user uploads.

### Batch 1 — July 2016 core

Preferred contents:

- `goa_human.gaf.159.gz`
- `goa_human.gpa.159.gz`
- `goa_human.gpi.159.gz`
- a contemporaneous GO OBO file if locally available
- the contemporaneous `gp2protein.geneid.gz` mapping if locally available

This batch establishes file semantics, identifier coverage, evidence distributions, ontology propagation, and the first complete label-reconstruction grid. It is prioritized for information gain, not because any earlier best-match claim is assumed true.

### Batch 2 — June 2016 comparison

- release 158 GAF/GPA/GPI triplet
- matching ontology/mapping files not already retained

### Batch 3 — September 2016 comparison

- release 160 GAF/GPA/GPI triplet
- matching ontology/mapping files not already retained

### Batch 4 — May 2016 legacy-format boundary

- release 157 `gene_association`, `gp_association`, and `gp_information`

Only request releases 155 and 156 afterward if release-boundary trends indicate they can distinguish candidate pipelines.

### Batch 5 — Entrez-native snapshots

One snapshot per upload when necessary:

- May 2016 `gene2go`
- December 2016 `gene2go`
- any June–September 2016 copy, with its original filename and acquisition history

### Batch 6 — Bioconductor packages

One package per batch because these archives can be comparatively large:

- `org.Hs.eg.db_3.3.0.tar.gz`
- `org.Hs.eg.db_3.4.0.tar.gz`
- earlier versions only if needed after comparing the 2016 pair

After extraction, the SQLite database metadata and all relevant Entrez–GO/UniProt maps are retained in normalized form before deletion clearance.

### Batch 7 — alternative upstream products

- HumanBase/GIANT gold-standard files
- any Sleipnir output, preprocessing code, intermediate label matrix, or node/label mapping from the earlier investigation

These are tested after the direct historical GO grids unless their inventory metadata shows a uniquely dated or irreplaceable artifact.

## Deletion clearance format

Deletion is authorized only with a message in this form:

```
SAFE TO DELETE — BATCH B###
- exact-file-name.ext — SHA-256: ...
- exact-file-name.ext — SHA-256: ...

Retained:
- derivative path and SHA-256
- batch receipt
- updated manifest and event log

No hold remains for these raw files.
```

A general statement such as “the batch is done” is not deletion authorization.

After deleting the attachments, the user should reply `Deleted B###`. The ledger will then record user-confirmed deletion; until that reply, the status remains `deletion_clearance_issued` rather than `deleted`.
